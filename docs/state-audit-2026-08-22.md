## 2. Unmatched label behaviour — diverges by vendor

This is confirmed to differ across all four vendors. There is no single "the adapter" behaviour.

**Rakuten** (`surveytool/ingest/rakuten.py:99-103`, `86-166`) — calls `classify_question_type()` (`surveytool/core/scale_library.py:104-133`). That function **never raises**: if `identify_family()` fails to match every label to one family, the question falls through to `QuestionType.categorical` with `roles=None`, silently, and no notice is recorded anywhere. A question whose labels partially match a family (some labels match, others don't) gets the identical categorical fallback as a question that matches nothing at all — there is no distinction in the output between "clearly not a scale" and "almost a scale, one label short."

**PureSpectrum** (`surveytool/ingest/purespectrum.py:142-146`) — identical code path to Rakuten: `classify_question_type()`, same non-raising categorical fallback. Confirmed live in §4: 8 of PureSpectrum's real questions are ordered scales by content (relevance, degree, importance, concern, worry, fluency wording) that fall to `categorical` with no error and no notice.

**Milieu** (`surveytool/ingest/milieu.py:231-245`) — for a `Single-select` column, first checks `any_label_matches_family(values)` (`scale_library.py:77-85`); if **no** label matches anything, it builds a plain `single_choice` question (line 239, never scale). But if **at least one** label matches a family, it calls `_build_scale_question`, which calls `resolve_roles()` (`scale_library.py:46-74`) — and `resolve_roles` **does raise** `UnresolvedScaleLabelsError` (`scale_library.py:72-73`) if any label in the set is left unresolved after the partial match. So a Milieu question with 4 labels where 1 matches a family and 3 don't hard-fails the load, wrapped and re-raised with the qid prefixed (`milieu.py:242-244`).

**Toluna** (`surveytool/ingest/toluna.py:211-217`) — identical logic to Milieu: `any_label_matches_family(values)` gate, then `_build_scale_question` → `resolve_roles()`, same raise-on-partial-match behaviour, same qid-prefixed re-raise (`toluna.py:214-215`).

**The finding, stated plainly:** Rakuten and PureSpectrum never fail on an unmatched or partially-matched scale — they silently demote to categorical. Milieu and Toluna fail the entire file load the moment any column has one matched label and one unmatched label. Two vendors that route through `classify_question_type` cannot produce `UnresolvedScaleLabelsError`; two vendors that route through `resolve_roles` (via `any_label_matches_family` as a gate) can and do, but only on partial matches — a wholesale non-match (no label matches anything) demotes silently on all four vendors identically, since `any_label_matches_family` returning `False` sends Milieu/Toluna to `single_choice` without ever calling `resolve_roles`.

## 3. Resolver reachability

`UnresolvedQuestionsError` (`surveytool/charts/errors.py:167-208`) is the structured, per-question error object the UI resolver is built to consume (`resolver-hint`, `unresolved-questions` DOM in `surveytool/desktop/static/index.html:301-435`). It is produced by exactly one function: `validate_all_questions()` in `surveytool/ingest/validate_questions.py:8-44`.

Grep across the full source tree confirms `validate_all_questions` is called from nowhere except its own test file (`tests/test_validate_questions.py`). It is not called by `rakuten.load`, `milieu.load`, `toluna.load`, `purespectrum.load`, `_load_survey`, `_run_pipeline`, or any endpoint in `surveytool/desktop/app.py`.

**Per vendor, whether a real file upload can reach the resolver via `UnresolvedQuestionsError`: no, for all four.** `validate_all_questions` also only ever fires on an *incomplete override* (`validate_questions.py:25-29`: `if override.question_type != "scale": continue`), not on a raw unmatched-label condition from a fresh load — so even if it were wired in, it could not be the source of the very first unresolved-questions report a new analyst would see; it is designed to check overrides already on file, not first-pass classification.

The error actually reachable from a real upload today, for Milieu and Toluna, is `UnresolvedScaleLabelsError` (§2), raised from inside `resolve_roles()` and propagated through `milieu.py:243-244` / `toluna.py:214-215` up through `_load_survey` (`app.py:264`) to the FastAPI exception handler (`app.py:84-88`), which serializes it via `SurveyToolError.to_response()` (`errors.py:85-91`) — a **flat** message/detail/next_action object with no `detail_entries` list, because `UnresolvedScaleLabelsError` does not override `to_response()` the way `UnresolvedQuestionsError` does. Its `next_action` text is literally "Add the missing labels to the scale library, or check the vendor setting" (`errors.py:155`) — the exact instruction the UI build plan says must be removed from the error card.

The frontend's per-question resolver DOM (`index.html:1307`, `resolverHint.textContent = entry.close_family_hint || ""`, `index.html:2134`) expects a `detail_entries` array with a `close_family_hint` field on each entry. Neither field exists anywhere in the object Milieu/Toluna's real failure produces, nor in `UnresolvedQuestion`'s serialized shape even when `UnresolvedQuestionsError` is raised directly in a test (`errors.py:199-207` — the fields serialized are `variable`, `question_text`, `codes`, `reason`; no `close_family_hint`).

**What would have to change for the resolver to be reachable:** `validate_all_questions` (or an equivalent single-pass check) would need to be called from inside `load()` for at least Rakuten and PureSpectrum before/instead of `classify_question_type`'s silent categorical fallback (§2), and from inside Milieu/Toluna's `parse_header` before/instead of raising `UnresolvedScaleLabelsError`, and the resulting `UnresolvedQuestionsError` would need a `close_family_hint` field computed and populated per entry.

## 5. Column classification fallback — per vendor

The approved design's function is `classify_columns()` in `surveytool/ingest/classify_columns.py:8-54`, which raises `UnclassifiedColumnError` (`surveytool/core/column_classification.py:17-33`) for any column matching none of its rules — "never silently skipped" per its own docstring.

**`classify_columns()` is called from nowhere in the runtime path.** Grep across `surveytool/` confirms its only caller is its own unit test (`tests/test_classify_columns.py`). It is not called by any of the four adapters' `load()` functions, nor by `app.py`.

The function actually used at runtime is `build_column_classifications()` in `surveytool/ingest/column_inventory.py:10-55`, called from `app.py:331` (`_build_session_run_summary`). Its fallback branch, verbatim: `if question is None: result[column] = ColumnClassification.UNCLASSIFIED` (`column_inventory.py:46-47`) — **no exception is raised.** An unrecognised column is placed into a plain Python dict under the `UNCLASSIFIED` key and returned; the run summary panel would show it, but nothing halts, and if the analyst never opens the run summary panel, an unclassified column is invisible.

Per vendor, run live against the real fixtures (verified in this session, §4's script plus a direct run of `build_column_classifications` against the Milieu fixture):

- **Rakuten**: `column_qid_map` (`rakuten.py:243-264`) is an identity map over the A1 header; every header column not in `RAKUTEN_PROFILE.reserved_metadata_columns`/`quality_columns` either has a matching `Question` (built by `parse_codebook`) or falls to `UNCLASSIFIED`. `tests/test_desktop_run_summary.py` (8 passed, confirmed in this session) does not include a Rakuten row in its `test_no_unclassified_columns_for_any_vendor` parametrization — only toluna/milieu/purespectrum are parametrized (see test file), so Rakuten's "no unclassified columns" claim is not independently test-verified in this suite, though no unclassified columns were observed in this session's manual runs against the two Rakuten fixtures.
- **Milieu**: verified directly in this session by loading `milieu_survey_coe_data.csv` and calling `build_column_classifications` — all 23 columns classify as `metadata` (14), `demographic` (2: q5, q6), or `question` (7: q7, q8, q10–q14). **Zero columns landed as `UNCLASSIFIED`, and zero landed as `question` that should have been `metadata`.** The specific claim from the prior report — that unrecognised Milieu columns get treated as questions — does **not hold against the current code and current fixture**: `MILIEU_PROFILE.reserved_metadata_columns` (`vendor_profile.py:83-87`) now lists all 14 non-bracketed columns actually present in this CSV's header, and `milieu.py`'s `parse_header` independently skips any column whose header doesn't match the `[qid]: qtype - text` regex (`milieu.py:201-204`, `_HEADER_RE`) before a Question is ever built — so even a column missing from `reserved_metadata_columns` would not become a spurious question column here, it would just never appear in `header_by_qid` and would classify `UNCLASSIFIED` via `column_inventory.py:44-47`, not `question`. This is confirmed for the one fixture in the repository; it is not a general proof for every possible Milieu export shape.
- **Toluna**: `column_qid_map` (`toluna.py:278-329`) re-derives qids via its own `parse_header` call. `tests/test_desktop_run_summary.py` includes toluna in the "no unclassified columns" parametrization and it passed in this session's full-suite run.
- **PureSpectrum**: `column_qid_map` (`purespectrum.py:263-304`) maps multiselect option columns to their group root; `tests/test_desktop_run_summary.py::test_purespectrum_all_42_columns_classified` and the `no_unclassified_columns` parametrization for purespectrum both passed in this session's run.

## 6. Declared but unwired

- **Non-substantive response label list** (`ToolConfig.nonsubstantive_labels`, `surveytool/core/config.py:17-19`). Declared, persisted per-project (`app.py:130-139`, `_load_project_settings`/`_save_project_settings`), presented and editable in the UI (`index.html:1824-1907`, the project-settings overlay with an add/remove label list), round-trips through `GET`/`POST /api/projects/{id}/settings` (`app.py:509-534`) and is asserted to round-trip in `tests/test_desktop_settings.py:34-45`. **The chain breaks at the classification boundary**: `is_nonsubstantive_label()` (`surveytool/core/nonsubstantive.py:20-21`) matches against a hardcoded module-level `_LABEL_PATTERNS` list (`nonsubstantive.py:8-15`, six fixed regexes) and takes no parameter for a configurable label list. Every call site across all four adapters (`rakuten.py:94`, `milieu.py:99,158,177`, `toluna.py:88,147`, `purespectrum.py:138`) calls `is_nonsubstantive_label(label)` with no settings argument. `settings.nonsubstantive_labels` is read in `app.py:516` only to echo it back in the settings-GET response; it is never passed into `_run_pipeline`, `build_findings_sheet`, or any classification function. A project that adds a custom label like "skipped" to its list has that label persisted and displayed, but it has zero effect on which responses get flagged nonsubstantive.

- **Exclude-from-base toggle** (`ToolConfig.exclude_nonsubstantive_from_base`). This one **is** wired: `app.py:375` passes `settings.exclude_nonsubstantive_from_base` into `build_findings_sheet` (`surveytool/findings/sheet.py:128,135,184,210`), which passes it into `frequency.py:98,112`'s `_base_responses(..., exclude_nonsubstantive=...)`. Confirmed live, not unwired.

- **Close-family hint.** The UI build plan describes rendering "the labels in this question look similar to the agreement scale" above the resolver's classification picker. No function anywhere in `surveytool/` computes a "closest matching family" or "near-miss" score — `scale_library.py` has no such function, only exact pattern membership (`_match_role`, `identify_family`). `UnresolvedQuestion` (`errors.py:159-164`) has no `close_family_hint` field, and its serialization (`errors.py:199-207`) does not emit one. The frontend nonetheless reads `entry.close_family_hint` (`index.html:2134`) into a dedicated `#resolver-hint` DOM element (`index.html:1307, 430-435`) — this will always render an empty string, since the field it reads does not exist on the object the backend can produce even in the one place `UnresolvedQuestionsError` is exercised (its own unit test).

- **PureSpectrum quality flag** (`PURESPECTRUM_PROFILE.quality_flag_column`). Declared as `None` in `vendor_profile.py:131`, with an inline comment marking it a deliberate placeholder pending vendor confirmation of QC2/QC2Flag's pass/fail coding. `QC2`/`QC2Flag` are classified `QUALITY` (`vendor_profile.py:130`, consumed by `column_inventory.py:41-42`) and excluded from question-building (`purespectrum.py:110-111`), so they are visible in the run summary but never used for filtering. `run_summary.py:25-34`'s `_quality_flag_statement` correctly reports "purespectrum supplies no quality flag column" for this reason — this is the one item in this section that is fully and correctly represented end to end as unavailable, not silently ignored.

- **`straightliner_action`** (`ToolConfig.straightliner_action: Literal["keep","exclude"] = "keep"`, `config.py:13`). Declared, defaults to `"keep"`. Never read anywhere — grep confirms no reference outside its own declaration. `app.py:370` calls `detect_straightliners()` unconditionally on every pipeline run and always excludes flagged respondents (`exclude_respondent_ids=excluded or None`, `app.py:373-376`) regardless of this setting's value. The declared default (`"keep"`) is the opposite of the tool's actual unconditional behaviour (always exclude when straightliners are detected).

Declaring `age_band` for Toluna as currently coded would raise `CanonicalCategoryUnreachableError` at registry-load time. Reason still holds; not independently re-verified against the raw Toluna fixture's column-2 values in this session (relies on the code comment's description of the fixture, not a fresh extraction).

**PureSpectrum** (`vendor_purespectrum.yaml`) — 2 dimensions mapped: `gender` (D3), `ethnicity` (D1). `age_band` (D2) excluded. **Verified directly in this session** by reading the Datamap sheet: D2 has exactly 10 bands — `18–24, 25–29, 30–34, 35–39, 40–44, 45–49, 50–54, 55–59, 60–64, 65+` (en-dash separators, confirmed present as literal `–` characters, which is exactly what `hygiene.py:7-11`'s `_DASH_FOLD` normalisation exists to handle in label matching — though note this normalisation applies to scale-label matching, not to demographic value_map keys, which are keyed by numeric code for PureSpectrum, not by label text). There is genuinely no "Below 18" band in D2. Given `canonical.yaml:26-51`'s `age_band` dimension requires `under_18` as a reachable category and `demographic_registry.py`'s reachability rule is enforced at registry load (not just a design intention), the exclusion reason stated in the YAML comment (`vendor_purespectrum.yaml:8-12`) is accurate as written: this is a genuine reachability gap under the current registry design, not a coding oversight, and not something the dash-normalisation utility could have resolved even if it were applied here (dash-folding does not invent a missing category). `D3` (gender) and `D1` (ethnicity) were checked and confirmed to be a direct code-for-code match to Rakuten's own S1/S4 canonical categories.

## 8. Override lifecycle — traced end to end

**Written**: the resolver-facing endpoint `POST /api/session/{session_id}/resolve` (`app.py:434-481`) accepts a batch of `ResolvedQuestionPayload` entries, builds a `QuestionOverride` per entry (`overrides.py:17-23`), and — for any entry with `question_type == "scale"` — calls `apply_override(labels, override)` (`overrides.py:56-63`) purely to validate completeness before any write happens (`app.py:464-466`, comment confirms: "validation happens in one pass before any write"). Only after every entry in the batch validates does the loop at `app.py:469-470` call `write_override()` once per entry.

**Stored**: `write_override()` (`overrides.py:98-107`) reads the existing `ProjectOverrides` YAML at the given path (or starts empty), sets `existing.overrides[override.variable] = override`, and writes the whole dict back with `yaml.dump`. Path is `_project_overrides_path(survey_id)` (`app.py:191-205`), one YAML file per `survey_id`, under `_OVERRIDES_DIR` (`tempfile.gettempdir()/surveytool-overrides`).

**Read on next load**: `_load_survey()` (`app.py:243-264`) calls `load_overrides(_project_overrides_path(survey_id)).overrides` (`app.py:263`) and passes the resulting dict into the vendor's `load()` function as its third positional argument, for all four vendors (`app.py:264`, `rakuten.load`/`milieu.load`/`toluna.load`/`purespectrum.load` all accept `overrides` as their third parameter per their signatures).

**Applied**: each vendor's classification path checks for a per-qid override before falling back to library classification. Rakuten/PureSpectrum: `resolve_with_override(substantive_norm, overrides, qid)` (`rakuten.py:99`, `purespectrum.py:142`), which returns `None` if no override exists for that qid (falls through to `classify_question_type`), or one of `excluded`/`scale` (via `apply_override`, which raises `IncompleteOverrideError` if any label lacks a role assignment, `overrides.py:56-63`)/`binary`/`categorical` (`overrides.py:69-95`). Milieu/Toluna: check `overrides.get(qid)` directly per-column and branch on `question_type` (`milieu.py:206-236`, `toluna.py:203-217`), calling `apply_override` for the scale case.

**Reflected in the run summary**: `_build_session_run_summary()` (`app.py:328-359`) reloads the project overrides (`app.py:335`) and builds `overrides_applied` as `(variable, resolved_at)` pairs filtered to only variables present in the current survey's questions (`app.py:337-341`). It also calls `check_override_still_needed()` per override (`overrides.py:116-132`) to generate a notice — non-blocking text — when the shared library would now also resolve a question that's still being overridden. Both `overrides_applied` and `override_notices` feed `build_run_summary()` (`run_summary.py:45-65`), which serializes them into `RunSummary.override_resolutions` and `RunSummary.notices`, both returned by `GET /api/session/{id}/run-summary` (`app.py:537-569`).

**Validation, and what happens on an incomplete or conflicting override**: validation happens at two points. (1) At write time in the resolve endpoint, `apply_override` is called before any file write, raising `IncompleteOverrideError` (`overrides.py:29-43`, code `UNRESOLVED_SCALE_LABELS`) if any label in the question's current label set lacks a role in `label_roles` — the app-level exception handler (`app.py:84-88`) turns this into a 400 response and the whole batch write is aborted (no partial write), confirmed by `tests/test_desktop_resolve.py::test_resolve_incomplete_scale_override_rejected` (passed in this session's run). (2) At load time, if a stored override somehow doesn't cover a question's current label set (e.g. the underlying file changed between resolve and re-run), `apply_override` inside `resolve_with_override`/the Milieu/Toluna branch would raise the same `IncompleteOverrideError` again — this is not separately tested for the load-time case in this session's run, so this half of the claim is **unverified against a live re-run with a changed file**; it follows from reading the shared `apply_override` function being the single implementation both call sites use, not from an executed test.

This lifecycle is identical in shape across all four vendors — the difference is only in where each adapter's classification branch calls `resolve_with_override` (Rakuten/PureSpectrum, one call) versus a direct `overrides.get(qid)` branch (Milieu/Toluna, inline per-column). Both converge on the same `apply_override` for the scale case.

## 10. Findings

Ranked by whether the defect can produce a wrong number that no one is told about, most severe first.

1. **PureSpectrum: 8 real ordered-scale questions silently net as categorical, with no error and no notice.** `surveytool/ingest/purespectrum.py:142-146` → `classify_question_type()` (`scale_library.py:104-133`) has no partial-match branch; `identify_family` requires every label in one family or it returns `None`, and the categorical fallback is silent by design (`scale_library.py:118-119`: "Never raises"). Verified in §4 against the real `purespectrum_survey_wcs_data.xlsx` codebook: Q4 (relevance), Q5/Q5A/Q5B (degree of fading), Q7 (importance), Q8 (concern), Q9 (worry), D5 (fluency) are all Likert-shaped attitude questions that a client would expect top-box/bottom-box netting on. A user viewing these questions in the tool would see a categorical breakdown (each option as its own row) with no netted top-two-box/bottom-two-box figure and **no indication that this differs from how the tool treats structurally identical scales on other vendors** — the output looks like a deliberate "this is a list, not a scale" classification, when it is actually a matcher miss. This is the highest-severity item: the output looks correct while silently omitting the netted metric a scale-shaped question would otherwise produce elsewhere in the same report.

2. **The resolver UI is built against an error shape the backend cannot produce from a real upload.** `UnresolvedQuestionsError` (`errors.py:167-208`), the only object carrying `detail_entries` (variable/question_text/codes/reason per question) that the resolver screen consumes, is only ever constructed by `validate_all_questions()` (`validate_questions.py:8-44`), which is called from nowhere except its own test (confirmed by full-repo grep, §3). The error actually raised on a real Milieu/Toluna partial-match failure, `UnresolvedScaleLabelsError`, has no `detail_entries` and tells the analyst to edit `scales.yaml` directly (`errors.py:155`) — the opposite of the intended UX. A user hitting this on Milieu or Toluna today gets a flat error card with instructions to edit a file they may not have access to, not the resolver.

3. **The close-family hint is entirely unimplemented, not merely unwired.** No function in `scale_library.py` or elsewhere computes a nearest-family match; `UnresolvedQuestion` has no field for it; the frontend reads a field (`entry.close_family_hint`, `index.html:2134`) that will always be `undefined`/empty. Lower severity than #1/#2 because it degrades a UI affordance, not a computed figure — but it means a documented feature (identifiable in the UI build plan and in visible frontend code) does not exist in the core at all.

4. **The configurable non-substantive-label list has no effect on classification.** `ToolConfig.nonsubstantive_labels` is fully wired for storage and display (`app.py:130-139, 509-534`; UI panel `index.html:1824-1907`) but `is_nonsubstantive_label()` (`nonsubstantive.py:20-21`) ignores it, matching only a hardcoded six-pattern list. A user who adds a custom label (e.g. "skipped", "not sure") via the settings panel, sees it saved and echoed back, and reasonably believes responses bearing that label are now excluded from bases/netting — they are not. This can silently change what should be excluded from a base without the analyst knowing the setting had no effect, which is a wrong-number-not-flagged risk, though bounded to whatever custom labels a project adds beyond the hardcoded six.

5. **`straightliner_action` config defaults to `"keep"` but the tool always excludes.** `config.py:13` declares `"keep"` as the default; `app.py:370-376` calls `detect_straightliners()` and always excludes flagged respondents unconditionally, regardless of this setting. The setting is never read anywhere. A project relying on the documented default behaviour (keep straightliners) would in fact have them excluded from every run, changing sample size and all derived percentages, without any code path that could be configured to stop it.

6. **`classify_columns()`/`UnclassifiedColumnError` — the approved "loud halt" design — is not wired into any load path.** The live path (`build_column_classifications`, `column_inventory.py:10-55`, called from `app.py:331`) puts an unmatched column into a dict under `UNCLASSIFIED` with no exception. This is visible only if the analyst opens the run summary panel (not automatic, per `app.py:539-543`'s own docstring). For the fixtures currently in the repository, no columns were observed to land as `UNCLASSIFIED` (§5), so this is a design gap without an currently-observed failure instance — but it means a genuinely new/unrecognised column in a future file would not halt the run the way the approved design specifies; it would sit unreported unless someone opens a panel that isn't shown by default.

7. **The "prior report" claim about Milieu columns is not reproducible against the current code and current fixture.** Directly tested in this session (§5): all 23 Milieu columns classify correctly (14 metadata, 2 demographic, 7 question), zero unclassified, zero misclassified-as-question. Recorded as a finding because the audit's brief specifically asked this be checked and the answer is that this particular defect does not currently reproduce — worth stating plainly rather than silently confirming or silently omitting.

8. **PureSpectrum Q9's codebook carries anomalous extra codes.** `purespectrum_survey_wcs_data.xlsx`'s Datamap entry for Q9 lists four worry-scale labels (codes 1–4) followed by `(0, 'Unchecked')` and `(1, 'Checked')` — a checkbox-shaped pair of codes appended to a single-select scale's code list, with a duplicate code value `1` used for both "Very worried" and "Checked". This is a property of the vendor file itself, discovered while running §4's script, not a tool defect — flagged here because it was directly observed and because a duplicate code key could affect downstream label lookups keyed by code if this question were ever netted (it currently is not netted, since it falls to categorical per finding #1).
